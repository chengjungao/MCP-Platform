# 设计文档：单 MCP Server 支持多 REST 服务

| 项目 | 内容 |
| --- | --- |
| 状态 | Accepted |
| 日期 | 2026-09-05 |
| 关联 | BR-1 / BR-2 / EXE-03 / EXE-04 / BR-4 |
| 关联 ADR | ADR-0001（Modern-only）、ADR-0002（base⊕overlay）、ADR-0003（流式桥接） |
| 需求来源 | 用户需求：一个 MCP Server 可注册多个 REST 服务 |

## 1. 背景与目标

### 1.1 现状

平台当前数据模型是 **1 MCP Server = 1 REST 服务 = 1 份 Swagger 文档**：

```
api_registration (1 Swagger) ──1:1 UNIQUE──> mcp_server ──1:N──> mcp_tool
                                                  │
                                                  └─ upstream: 单个 UpstreamSnapshot JSONB
                                                     (baseUrls + LB + 超时/重试/熔断)
```

所有 tool 隐式共用 server 的唯一 upstream。这在「一个 MCP Server 桥接一个微服务」的场景下成立，但当**一个业务域横跨多个微服务**（例如订单域 = 订单服务 + 库存服务 + 支付服务）时，用户被迫为每个微服务建一个 MCP Server，PATH 末段碎片化、消费方需配置多个端点。

### 1.2 目标

**一个 MCP Server 可注册多份 Swagger（多个 REST 服务），每份有独立 upstream / Auth-B / 熔断，tool 注册时自动绑定到其所属服务的上游。**

### 1.3 语义边界（已与用户确认）

- **聚合语义**：1 MCP Server 绑 N 份 Swagger/registration，每份是独立 REST 服务
- **Tool 归属**：注册时自动绑定——每份 Swagger 解析出的 tool 自动绑定到该 Swagger 的 upstream，快照里 tool 带 `upstreamRef` 指向所属服务
- **不混用**：OpenAPI 的 `servers[]` 仍是同一服务的多实例 LB，不是多服务；多服务只通过多 registration 接入

## 2. 核心设计

### 2.1 设计原则：沿用 `effectiveAuthB` 同构模式

代码里已有「Server 级默认 + Tool 级覆盖」的成熟模式——`UpstreamCredentialProvider.effectiveAuthB(server, tool)`（`mcp-executor/.../auth/UpstreamCredentialProvider.java:115-121`）。多上游采用**完全同构**的结构：

- Server 持有一组上游（`List<UpstreamEntry>`，按 `serviceId` 索引）
- Tool 带一个 `upstreamRef`（String，指向 `UpstreamEntry.serviceId`）
- 运行时 `effectiveUpstream(server, tool)` 按 ref 查找，与 `effectiveAuthB` 同构

**为什么不每个 tool 内嵌整个 UpstreamSnapshot？**——冗余、快照膨胀、且 tool 无法感知同服务其他 tool 的 upstream 变化。ref 模式让 upstream 配置一处改、所有引用它的 tool 生效。

### 2.2 数据模型变更

#### 2.2.1 关系表（Flyway 新增 V2 迁移）

| 表 | 改动 |
| --- | --- |
| `mcp_server.registration_id` | **去掉 UNIQUE 约束**，改为普通 FK（N:1） |
| `mcp_server.upstream` | **删除该列**（迁移到 `server_upstream` 表） |
| **`server_upstream`（新表）** | 见下方 DDL |
| `mcp_tool` | **新增 `upstream_ref VARCHAR(64)` 列**（指向 `server_upstream.service_id`） |
| `mcp_tool` 唯一约束 | `uk_tool_server_anchor` 扩展为 `uk_tool_server_upstream_anchor (server_id, upstream_ref, anchor)`——同名 tool 跨服务允许重复 |

**`server_upstream` 表 DDL：**

```sql
CREATE TABLE server_upstream
(
    id              BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    server_id       BIGINT       NOT NULL REFERENCES mcp_server (id) ON DELETE CASCADE,
    service_id      VARCHAR(64)  NOT NULL,          -- 业务标识，tool.upstream_ref 指向它
    name            VARCHAR(128) NOT NULL,          -- 展示名（来自 Swagger info.title）
    base_urls      JSONB        NOT NULL,           -- List<String>，同服务的多实例 LB
    lb_strategy     VARCHAR(16) NOT NULL DEFAULT 'ROUND_ROBIN',
    weights         JSONB,                           -- List<Integer>
    connect_timeout BIGINT       NOT NULL DEFAULT 3000,
    read_timeout   BIGINT       NOT NULL DEFAULT 30000,
    retries         INT          NOT NULL DEFAULT 1,
    retry_on_status JSONB,                           -- List<Integer>
    circuit_breaker JSONB,                           -- {failureThreshold, openMs, halfOpenProbes}
    auth_b          JSONB,                           -- AuthBSnapshot，本服务专属上行鉴权
    created_at      TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at     TIMESTAMPTZ,
    UNIQUE (server_id, service_id)
);
CREATE INDEX idx_server_upstream_server ON server_upstream (server_id);
```

### 2.3 快照模型变更（mcp-common，Executor 运行时加载）

#### 2.3.1 `ServerSnapshot`

```java
// 变更前
UpstreamSnapshot upstream,

// 变更后
List<UpstreamEntry> upstreams,   // 多个，按 serviceId 索引
```

新增 `UpstreamEntry` record（与 `UpstreamSnapshot` 平级）：

```java
@JsonInclude(JsonInclude.Include.NON_NULL)
public record UpstreamEntry(
    String serviceId,           // 业务标识，tool.upstreamRef 指向它
    String name,                // 展示名（来自 Swagger info.title）
    UpstreamSnapshot config,    // baseUrls + LB + 超时/重试/熔断
    AuthBSnapshot authB         // 本服务专属上行鉴权（原 server.authB 下沉到此）
) {
    public static UpstreamEntry single(String serviceId, UpstreamSnapshot config) {
        return new UpstreamEntry(serviceId, serviceId, config, null);
    }
}
```

新增运行时查找方法（同 `effectiveAuthB` 模式）：

```java
public Optional<UpstreamEntry> upstream(String serviceId) {
    if (upstreams == null || serviceId == null) return Optional.empty();
    return upstreams.stream().filter(u -> serviceId.equals(u.serviceId())).findFirst();
}

/** 运行时：按 tool.upstreamRef 查找所属上游；ref 为空时回落到第一个（向后兼容）。 */
public UpstreamEntry effectiveUpstream(ToolSnapshot tool) {
    String ref = tool == null ? null : tool.upstreamRef();
    Optional<UpstreamEntry> hit = upstream(ref);
    if (hit.isPresent()) return hit.get();
    if (upstreams != null && !upstreams.isEmpty()) return upstreams.get(0);
    return UpstreamEntry.single("default", UpstreamSnapshot.defaults(List.of()));
}
```

#### 2.3.2 `ToolSnapshot`

```java
// 新增字段
String upstreamRef,   // 指向 UpstreamEntry.serviceId；注册时自动绑定
```

**Tool 命名规则（R2 决策）**：多服务接入时 tool 名 = `<serviceId>_<baseName>`（服务前缀）。例如两份 Swagger 都有 `getUser`，分别属 `order` 和 `inventory` 服务时，生成 `order_getUser`、`inventory_getUser`，单 Server 内 name 仍唯一（满足 `^[a-zA-Z0-9_-]{1,64}$`）。`ToolNames.unique` 扩展为自动加服务前缀，无需人工干预。

### 2.4 运行时调用链变更（mcp-executor）

**`UpstreamInvoker.invoke` 核心改动：**

```java
// 变更前
UpstreamSnapshot upstream = server.upstream() != null ? server.upstream() : UpstreamSnapshot.defaults(List.of());

// 变更后
UpstreamEntry entry = server.effectiveUpstream(tool);
UpstreamSnapshot upstream = entry.config();
AuthBSnapshot authB = entry.authB() != null ? entry.authB() : server.authB();  // 服务级优先，回落 Server 级
```

**熔断器与轮询计数器的 key 改动（关键不变量）：**

```java
// 变更前（错误：多服务共享熔断）
breakers.allow(server.serverId(), breakerConfig);
counters.computeIfAbsent(server.serverId(), ...);

// 变更后（按服务隔离）
String breakerKey = server.serverId() + ":" + entry.serviceId();
breakers.allow(breakerKey, breakerConfig);
counters.computeIfAbsent(breakerKey, ...);
```

**理由**：当前熔断器按 `serverId` 隔离，多上游后服务 A 连续失败会误熔断服务 B——这是探查发现的既有潜在缺陷（单上游时隐蔽，多上游时暴露）。改为 `serverId:serviceId` 复合 key。

### 2.5 存储形态选择：独立表 vs JSONB 数组

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| **A. 独立 `server_upstream` 表** | 可独立 CRUD、审计粒度细、auth_b 下沉自然 | 多一张表 + 实体 + repo |
| B. `mcp_server.upstreams` JSONB 数组 | 无新表、改动小 | 整体替换、无独立审计、auth_b 下沉后字段重复 |

**选 A**——独立表。理由：① 多服务的 Auth-B 各异（当前 `mcp_server.auth_d` 是单值，多服务后 auth_b 必须下沉到 upstream 维度，独立表最自然）；② CRUD 语义清晰（增删某个服务不影响其他）；③ 与既有 `auth_config` 表的治理模式一致。

## 4. 迁移（不做兼容）

**平台未上线，无生产数据，不做向后兼容处理。** 直接破坏性变更：

- Flyway 新增 `V2__multi_upstream.sql`：建 `server_upstream` 表 + 改 `mcp_server.registration_id` 去 UNIQUE + 删 `mcp_server.upstream` 列 + `mcp_tool` 加 `upstream_ref` 列
- `ServerSnapshot` 直接改字段（`upstream` → `upstreams`），不加 `@JsonAlias`、不加反序列化兼容层
- 旧 `PUT /servers/{id}/upstream` API 直接删除，替换为 `PUT /servers/{id}/upstreams/{serviceId}`，不做 410 Gone 引导

理由：与 ADR-0001 Modern-only 同一原则——P0 阶段无生产客户端，不做双栈、不做兼容转换。包袱是我们自己背上去的。

`V2__multi_upstream.sql` 内容：

```sql
-- 1. 建 server_upstream 表（见 §2.2.1 DDL）

-- 2. 去掉 mcp_server.registration_id 的 UNIQUE 约束
ALTER TABLE mcp_server DROP CONSTRAINT IF EXISTS mcp_server_registration_id_key;

-- 3. 删除 mcp_server.upstream 列
ALTER TABLE mcp_server DROP COLUMN upstream;

-- 4. mcp_tool 新增 upstream_ref
ALTER TABLE mcp_tool ADD COLUMN upstream_ref VARCHAR(64);
ALTER TABLE mcp_tool DROP CONSTRAINT IF EXISTS uk_tool_server_anchor;
ALTER TABLE mcp_tool ADD CONSTRAINT uk_tool_server_upstream_anchor UNIQUE (server_id, upstream_ref, anchor);
```

## 5. 不变量（改动后必须守住）

| # | 不变量 | 验证点 |
| --- | --- | --- |
| 1 | Modern-only 守卫不退化 | 流式/多上游请求仍是 2026-07-28，`ProtocolGuard` 不变 |
| 2 | 原始 Swagger 只读 + sha256 不退化 | 多 Swagger 各自独立只读，每份 sha256 校验不变 |
| 3 | Executor 无状态、不引入会话路由 | `effectiveUpstream` 是纯函数，无状态；SSE 流仍 request-scoped |
| 4 | 熔断按上游隔离，不按 server 共享 | `breakerKey = serverId:serviceId` |
| 5 | tool 名规则不变 | `^[a-zA-Z0-9_-]{1,64}$`；跨服务同名允许，单服务内唯一 |
| 6 | PATH 末段仍是稳定契约 | 多服务接入不改 PATH 语义，末段仍是 Server 级 |

## 6. 风险与开放问题

| # | 风险 | 影响 | 缓解 |
| --- | --- | --- | --- |
| R1 | 同名 tool 跨服务重复，消费方 `tools/call` 只传 name 不传 serviceId | tool 定位歧义 | 唯一约束改 `(server_id, upstream_ref, anchor)`；`tools/list` 的 tool name 在单 Server 内仍需唯一（注册时去重） |
| R2 | 多 Swagger 合并时 tool 命名冲突（两份 Swagger 都有 `getUser`） | 注册失败或 tool 名不可读 | **决策：服务前缀去重**——`<serviceId>_<baseName>`（如 `order_getUser`、`inventory_getUser`）。`ToolNames.unique` 扩展为跨服务全局加前缀，单 Server 内 name 唯一约束仍成立 |
| R3 | 快照体积膨胀（N 个 upstream + 每个 auth_b） | 网络传输、Executor 内存 | 单 Server 上游数预期 < 20；auth_b 是掩码后的快照不泄密；监控快照大小 |
| R4 | `server_upstream.service_id` 命名冲突（两份 Swagger 同 title） | 注册时 UNIQUE 冲突 | serviceId 用 `registrationId` 或 `slug(title)#shortHash`，不依赖用户输入 |
| R5 | Auth-B 下沉到 upstream 后，既有 `auth_config` 表（Server 级）的迁移 | 旧数据 auth_b 丢失 | V2 迁移把 `auth_config` 的 server 级 auth_b 复制到 `server_upstream.auth_b`，保留 server 级作回落 |
| R6 | overlay 的 tool 级 `authBOverride` 与 upstream 级 auth_b 优先级 | 语义冲突 | 优先级：tool.authBOverride > upstream.authB > server.authB（最具体优先） |

## 7. 实施顺序（建议）

按依赖关系分层推进，每层可独立编译验证：

1. **mcp-common 快照模型**：`ServerSnapshot` / `ToolSnapshot` / `UpstreamEntry` + 反序列化兼容
2. **Flyway V2 迁移 + JPA 实体**：`ServerUpstream` 实体 + `McpServer`/`McpTool` 字段调整
3. **mcp-manager 服务层**：`SnapshotAssembler` / `ServerService` / `RegistrationService` / `PublishService`
4. **mcp-manager DTO + Controller**：API 形态变更
5. **mcp-executor 运行时**：`UpstreamInvoker` / `CircuitBreakerRegistry` / `UpstreamCredentialProvider`
6. **测试更新**：5 个测试文件夹具
7. **mcp-manager-ui**：types + UpstreamPanel
8. **端到端验证**：注册 2 份 Swagger → 发布 → MCP 客户端调用不同服务的 tool

## 8. 验收标准

1. 一个 MCP Server 可挂载 ≥2 份 Swagger，各自独立 upstream / Auth-B
2. 注册时 tool 自动绑定 `upstreamRef`，无需人工配置
3. `tools/list` 列出所有 tool（跨服务），name 在 Server 内唯一
4. `tools/call` 命中不同服务的 tool 时，Executor 路由到正确 upstream
5. 服务 A 连续失败熔断，不影响服务 B 的调用（breakerKey 隔离）
6. 既有单上游 Server 升级后无需改配置（V2 迁移 + 快照兼容）
7. 三条不变量（Modern-only / sha256 / 无状态）不退化

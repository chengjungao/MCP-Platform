# MCP Server 跨部门访问申请（Cross-Dept Access）设计

状态：**Accepted**（2026-09-05 用户确认 D1–D4 后已实施：V4 建表 + requireManage/requireRead 拆分 + AccessService/Controller + 前端访问申请页与只读详情；另按完整闭环补充 GET /access/grants 用于资源方回收已授权）
项目：MCP-Platform
日期：2026-09-05

## 背景与目标

当前部门隔离（`DepartmentScope`）只允许：本部门 + 子部门可见可管，平台管理员不受限，其余一律 403。
`DepartmentScope` 注释宣称「跨部门访问需显式授权」，但**尚无任何授权机制**。

本功能补上这条闭环：

- 本部门的人正常管理本部门的 MCP Server（现状不变）
- 其他部门持有读权限（`server:read`）的用户可以**按部门申请**访问某 MCP Server
- 审批人 = **Server 所属部门的部门管理员（DEPT_ADMIN）+ 平台管理员**（资源方授权）
- 通过后申请部门获得该 Server 的**只读访问**（看详情 / Tool 列表），写操作仍只限所属部门

## 已确认决策（D1–D4）

| 决策 | 结论 |
|---|---|
| D1 审批人 | Server 所属部门的 DEPT_ADMIN + PLATFORM_ADMIN（资源方授权） |
| D2 授权粒度 | 只读访问：详情 / Tool 列表；不含 Auth-B/Auth-D 凭据，不含任何写操作 |
| D3 申请粒度 | 按部门申请、整部门授权（一个部门一次申请，该部门成员共享；覆盖部门子树，与既有「部门管理员可见子孙部门」语义一致） |
| D4 发现方式 | 独立「访问申请」页（申请目录 / 我发起的 / 待我审批 三个 tab），Server 列表保持本部门隔离 |

## 权限语义拆分（关键）

现状 `ServerService.requireServer` 读写共用（只做部门树校验）。放开跨部门读后**必须拆开**，
否则外部门持全局 `server:write`/`auth:write` 角色的人（如 DEPT_DEVELOPER、OPS）在获批后能绕开只读边界写配置。

| 校验 | 语义 | 适用接口 |
|---|---|---|
| `requireManage(id, principal)` | 部门树内（现状逻辑）：本部门/子部门/平台管理员 | 全部写操作 + Auth-B/Auth-D 凭据读取（含 GET） |
| `requireRead(id, principal)` | 部门树内 **或** 该 Server 有 APPROVED 授权覆盖申请人部门 | `GET /servers/{id}`、`GET /servers/{id}/tools` |

- 读集合刻意收窄：`view` + `tools`。diff / effective / bindings / auth-b / auth-d 不对外部门授权用户开放
- 前端只读态由 `ServerView.manageable`（后端算好）驱动，**不依赖前端权限点判断**（堵住全局写角色漏改）

## 数据模型

新表 `server_access`（Flyway V4），按 (server, dept) 唯一：

```sql
CREATE TABLE server_access (
    id            BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    server_id     BIGINT      NOT NULL REFERENCES mcp_server (id) ON DELETE CASCADE,
    dept_id       BIGINT      NOT NULL REFERENCES department (id),
    status        VARCHAR(16) NOT NULL,            -- PENDING / APPROVED / REJECTED / REVOKED
    reason        VARCHAR(500),                    -- 申请理由
    requested_by  BIGINT      NOT NULL,            -- 申请人 userId（审计）
    requested_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    reviewed_by   BIGINT,                          -- 审批人 userId
    reviewed_at   TIMESTAMPTZ,
    review_note   VARCHAR(500),                    -- 审批意见
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ,
    CONSTRAINT uk_server_access UNIQUE (server_id, dept_id)
);
CREATE INDEX idx_server_access_dept ON server_access (dept_id);
CREATE INDEX idx_server_access_status ON server_access (status);
```

状态机：`PENDING → APPROVED / REJECTED`；`APPROVED → REVOKED`（所属部门可回收）；`REJECTED → PENDING`（可带新理由重新申请）。

实体 + 仓储：`ServerAccess`（枚举 `AccessStatus`）、`ServerAccessRepository`
（`findByServerId` / `findByDeptIdIn` / `findByStatusAndServerIdIn` 等）。

## 授权判定

主查询加一层（跨部门读）：

```
hasRead(server, principal) =
    平台管理员                                        -- 现
  ∨ principal.deptId ∈ 子树(server.deptId)            -- 现（含祖先部门管子孙）
  ∨ ∃ APPROVED server_access(server, D) 且 D ∈ {principal.deptId} ∪ 祖先链(principal.deptId)
```

`accessGrantsForDeptChain`：一次性取出 principal 部门链上的授权，避免逐 server 查询。

## 接口（新 `AccessController`，前缀 /access，全部需登录）

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/api/v1/access/catalog` | `server:read` | 可申请目录：principal **不可访问**的 Server 最小信息（id/name/pathSegment/deptName/status/接口数 + 我的申请状态），分页 |
| POST | `/api/v1/access` | `server:read` | 发起申请 `{serverId, reason}`；申请部门=principal 所属部门；已 PENDING→冲突，REJECTED→覆盖重提，APPROVED/自身可访问→拒绝 |
| GET | `/api/v1/access/mine` | `server:read` | 我（本部门树）发起的申请列表，带 Server 名/状态/审批意见 |
| GET | `/api/v1/access/todo` | `server:read` + 审批资格 | 待我审批：PENDING 且 server.deptId ∈ 我的部门树；审批资格=平台管理员或 DEPT_ADMIN |
| POST | `/api/v1/access/{id}/approve` | 审批资格 + 资源方 | `{note}` → APPROVED |
| POST | `/api/v1/access/{id}/reject` | 同上 | `{note}` → REJECTED |
| POST | `/api/v1/access/{id}/revoke` | 资源方管理权 | 仅 APPROVED 可回收 → REVOKED |

审批资格判定：`principal.isPlatformAdmin() || roles 含 DEPT_ADMIN`，且 `server.deptId ∈ visibleDeptIds(principal)`。

审计：申请/审批/回收均走 `AuditService`（新增 `ACCESS_APPLY/ACCESS_APPROVE/ACCESS_REJECT/ACCESS_REVOKE` 动作）。

## 影响面与风险

- **行为变化**：`requireServer` 拆开后所有既有读写路径语义不变（部门树内行为与现状一致），仅新增读路径放行条件；回归面主要在 PublishService 与 ServerController auth-b/d（改用管理校验，语义不变）
- **凭据保护**：Auth-B（上行凭据）/ Auth-D（下行验签）GET 收紧为 `requireManage`，跨部门只读用户即使有全局读权限也拿不到
- **不做**：跨部门 Server 出现在本部门 Server 列表；授权写权限；Execuutor/客户端侧 MCP 调用授权（那是另一层的问题，本期只覆盖控制台管理面）
